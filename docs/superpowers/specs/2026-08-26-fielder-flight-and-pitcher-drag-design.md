# 야수 · 화면을 쓰는 타구 · 투수 드래그 — 설계

2026-08-26

## 목표

세 가지를 한 번에 얹는다. 셋 다 「지금 게임이 얇은 자리」를 겨눈다.

1. **야수를 세운다.** 지금은 담장 앞에 떨어지면 전부 안타다. 빗맞은 땅볼도 안타,
   담장 코앞의 대형 뜬공도 똑같이 안타라서 **「잘 맞았는데 잡혔다」가 없다.**
   외야수 한 명이 낙구 지점으로 달려가 제때 닿으면 아웃이다.
2. **타구가 화면을 쓰게 한다.** 컨셉 문장은 「작업 중인 창 위로 포물선을 그리며
   날아간다」인데, 정작 포물선이 안 보인다 — 잔상이 130ms짜리 짧은 꼬리라서 공만 보인다.
   그리고 파울은 뒤로 세게 나가 **뜨자마자 화면 밖으로 사라진다.** 파울이라는 결과가
   화면에서 아무 일도 안 일으킨다.
3. **투수를 드래그해서 옮긴다.** 난이도를 플레이어가 정한다. 투수를 당기면 공이 일찍
   도착해 반응 시간이 진짜로 줄고, 밀면 늘어난다.

## 확정된 결정

- **아웃은 잃는 게 없다.** 「아웃」은 그 타석의 결말 이름일 뿐이다. `streak`도 안 끊고,
  다음 공은 똑같이 온다. 「볼·스트라이크 카운트 없음」과 같은 이유다 —
  이건 몰래 손 푸는 게임이지 지고 이기는 게임이 아니다. 아웃카운트는 넣지 않는다.
- **아웃은 타이밍이 아니라 타구가 정한다.** 홈런이 그런 것처럼. `judgeSwing`은 절대
  `OUT`을 돌려주지 않는다 — 궤적을 만들어 봐야 알 수 있는 값이기 때문이다.
- **야수는 뛰어간다.** 못 박아 두면 담장과 똑같은 물건, 그냥 구멍 뚫린 낮은 벽이 되고
  몇 판이면 「저기만 피하면 된다」로 굳는다. 달리는 속도가 상수 하나라 여전히
  결정론적이고, 「보이는 그대로 판정된다」도 안 깨진다.
- **잡는 건 뜬공뿐이다.** 바운드된 공은 안 잡는다. 규칙이 한 줄이고 야구답다.
- **담장은 화면 폭 97%에 그대로 둔다.** 안쪽으로 당기면 홈런이 화면을 더 가로지르지만
  안타·파울이 돌아다니는 범위가 같이 좁아진다.
- **파울은 얇고 빠르게, 홈런은 길고 진하게.** 파울은 헛스윙 다음으로 흔하다.
  자주 나오는 결과를 크게 그리면 「몰래」가 깨진다.
- **투수 이동 범위는 좁다(±15% 안팎).** 최고 비거리 기록을 하나로 두기 때문이다.
  범위가 넓으면 멀찍이 밀어 두고 세운 기록이 판을 차지한다.
- **클릭 통과에 예외를 딱 한 군데 판다.** 커서가 투수 히트박스 안에 있고 수식키를
  누르고 있는 그 순간에만 창이 마우스를 받는다. 그 밖의 모든 순간·모든 자리는
  지금처럼 전부 통과한다.
- **셸은 문만 여닫는다.** 드래그 로직은 전부 웹뷰 쪽 JS다. 네이티브에 새로 생기는 건
  `ignoresMouseEvents` 토글 하나뿐이다.

## 1. 새 결과 `OUT`

`judge.js`에 상수와 이름만 더한다.

```js
export const OUT = 'out'
LABELS[OUT] = '아웃'
```

`judgeSwing`은 바뀌지 않는다. **`OUT`을 반환하지 않는다는 사실을 주석으로 못 박는다** —
홈런이 그렇듯 아웃도 engine이 궤적을 보고 정한다.

`engine.applyResult`의 판정 순서:

```
안타로 맞았다 → battedFlight 로 궤적을 만든다
  → clearsFence(flight)      → HOMERUN
  → chase(flight)?.caught    → OUT
  → 아니면                    → HIT
```

파울은 뒤로 가므로 `chase`를 묻지 않는다.

`hits`는 안 올린다 — 아웃은 안타가 아니다. `streak`도 **올리지도 끊지도 않는다**
(「아웃은 잃는 게 없다」).

기록은 그대로다 — 아웃도 비거리가 있는 타구이므로 `bestMeters` 갱신 대상이다.
(잡힌 타구도 「얼마나 멀리 칠 뻔했는지」는 말해 준다. `distance()`가 이미 담장을
무시하고 그 값을 주고 있다.)

### 잡힌 공은 거기서 멈춘다

지금 시간 계산이 전부 **「공이 다 굴러 멈추는 순간」** 하나를 기준으로 돈다 —
`restAt`(다음 투구), `outcomeLife`(글씨가 뜨는 시각), `drawOutcome`의 위치.
아웃을 그냥 얹으면 **야수가 잡았는데 공은 야수를 지나쳐 계속 굴러가고**, 글씨도
굴러 멈춘 자리에 뜬다.

그래서 아웃일 때는 **궤적이 `hangMs`에서 끝난 것으로 친다.** 홈런이 `overAtMs`에서
끝나는 것과 똑같은 처리이고, 이미 그 자리가 코드에 나 있다.

| | 궤적이 끝나는 시각 | 글씨가 뜨는 자리 |
|---|---|---|
| 홈런 | `flight.overAtMs` | 담장 위 |
| **아웃** | **`chase().hangMs`** | **잡힌 자리(`spotX`)** |
| 안타·파울 | `roll.startMs + roll.durMs` | 공이 멈춘 자리 |

- `engine.applyResult`: `restAt = now + hangMs / TIME_SCALE`,
  `outcomeLife`도 `hangMs` 기준. 잘 맞아 잡힌 타구는 체공이 길어 다음 공이 늦게 온다 —
  「잘 맞을수록 다음 공이 늦게 온다」가 그대로 유지된다.
- `draw.drawFlight`: 공을 `hangMs`까지만 그린다. 그 뒤엔 야수 글러브 안이다.
- `draw.drawOutcome`: 아웃의 `atMs`는 `hangMs`, 자리는 `space.origin.x + spotX × unitX`.

## 2. `src/game/fielder.js` — 다섯 번째 순수 모듈

`batted.js`(246줄)는 물리로 이미 꽉 차 있다. 야수는 **「궤적이 주어졌을 때 사람이
거기 닿는가」**라는 독립된 질문이고, 인터페이스가 한 줄로 떨어진다.

```js
export const START_X   = 1.9   // 처음 서 있는 자리 (타격점에서, 필드 높이 단위)
export const RUN_SPEED = 1.15  // 필드 높이 / 초
export const REACH     = 0.14  // 글러브가 닿는 반경

export function chase(flight) // → { caught, spotX, needMs, hangMs } | null
```

`batted.js`가 이미 필요한 것을 전부 내주고 있다 — `carry(flight)`가 첫 구간이 끝나는
거리(낙구 지점)를, `flight.hops[0].durMs`가 체공 시간을 준다. 새로 계산할 물리가 없다.

규칙:

- `flight.over`면 `null`. 담장을 넘은 공은 야수가 관여하지 않는다.
- **첫 구간이 땅에 닿아 끝난 경우에만** 기회가 있다. 담장을 직격한 라이너는
  공중에서 벽에 막힌 것이라 못 잡는다 — `hops[0]`이 벽에서 끊겼으면 `null`.
- `spotX = min(carry(flight), FENCE_DIST)`. 야수는 담장 밖으로 안 쫓아간다.
- `needMs = max(0, |spotX − START_X| − REACH) / RUN_SPEED × 1000`
- `caught = needMs <= hangMs`

이 상수 세 개가 난이도의 전부다. 대략 이렇게 갈린다:

| 타구 | 낙구 | 체공 | 결과 |
|---|---|---|---|
| 빗맞아 힘없는 공 | 가깝다 | 짧다 | 야수가 못 온다 — **안타** |
| 잘 맞았지만 담장을 못 넘김 | 야수 근처 | 길다 | **아웃** |
| 낮게 깔린 라이너 | 멀다 | 아주 짧다 | 못 온다 — **안타** |
| 담장을 넘김 | — | — | **홈런** |

야구에서 제일 허무한 장면이 그대로 생긴다. 잘 맞힐수록 홈런 아니면 아웃이고,
어중간하게 맞은 공이 안타가 된다.

## 3. 렌더 — 야수

`sprites.js`에 외야수 포즈를 더한다: **대기 / 달리기 / 포구** 셋. 타자·투수 포즈와
같은 방식이다(검은 실루엣 위에 살색과 유니폼).

`draw.js`는 `chase()`가 준 값으로 위치만 보간해 그린다. **렌더가 물리를 다시
계산하지 않는다** — 담장이 그런 것처럼 판정에 쓴 값을 그대로 그린다.

- 타구가 없을 땐 `START_X`에 대기 포즈로 서 있는다.
- 타구가 뜨면 `START_X → spotX`로 `needMs` 동안 달린다(달리기 포즈).
- `caught`면 `hangMs` 시점에 포구 포즈.
- 유니폼은 **투수 팀 키트**를 입는다.

야수는 필드 상자 밖, 화면 한가운데쯤 지면선 위에 선다. 지면선은 `drawGround`가 이미
`space.fenceX`(화면 폭 97%)까지 긋고 있으므로 새로 그릴 게 없다.

**CLAUDE.md 갱신 대상:** 「선수·지면·담장·투구는 필드 상자 안에만」은 지금도 사실이
아니다(지면·담장은 이미 상자 밖 화면 좌표다). 「**타자·투수·투구만 상자 안**」으로 고친다.

## 4. 연출 — 홈런과 파울

### 홈런: 포물선을 그린다

`TRAIL_MS = 130`은 공 뒤에 붙은 짧은 꼬리라 궤적이 아니라 공만 보인다.
**결과별로 나눈다** — 홈런은 500ms. 화면을 가로지르는 포물선 자체가 그려지고,
그제야 컨셉 문장이 화면에 나타난다. 안타·아웃은 지금 값 그대로다.

담장 위치는 안 건드린다. 홈런의 비행은 대부분 담장 도달 **전**이고, 그 구간이
이미 화면 폭 97% × 화면 높이 절반쯤을 쓴다 — 안 보였던 건 거리가 아니라 잔상이었다.

### 파울: 팝파울로 바꾼다

지금 `FOUL_SPEED_RATIO = -0.5`. 뒤로 세게 나가는데 타격점이 화면 왼쪽 끝에서
50px밖에 안 떨어져 있어서 뜨자마자 화면 밖이다.

- 뒤로 가는 힘을 `-0.15`로 줄인다.
- 파울일 때 발사각을 `MAX_DEG` 근처로 올린다.

거의 수직으로 솟아 타격점 바로 위에서 화면 천장까지 올라갔다 돌아온다.
**잔상 없이, 글로우도 낮게** — 홈런과 정반대로 얇고 빠르게 지나간다.
자주 나오는 결과이므로 조용해야 한다.

## 5. 투수 드래그

### 거리가 곧 시간이다

`PITCHER_X = 0.87`은 지금 `draw.js`에 있는 그림용 상수다. 이제 판정에 들어가므로
**순수 모듈로 내려간다.** `nextPitch`가 거리를 받아 `flightMs`를 비례로 늘리고 줄인다.

```js
nextPitch(homeRuns, rand, distanceRatio = 1)
// flightMs = round(def.flightMs × speedFactor(homeRuns) × distanceRatio)
```

투수를 당기면 `distanceRatio < 1` — 공이 일찍 오고 반응 시간이 줄어든다.
담장이 그랬듯 **보이는 그대로 판정된다.**

범위는 좁다: 기본 위치 기준 **±15% 안팎**. 아래 「남은 판단」 참고.

### 문은 셸이 여닫고, 드래그는 웹뷰가 한다

이게 이 절의 핵심이다. 네이티브에 드래그 코드를 안 쓴다.

1. **게임 → 셸**: 투수가 화면 어디에 그려지는지는 `draw.js`만 안다.
   브리지로 밀어 준다 — `sneaky.setHitbox({ x, y, w, h })`. 창 크기가 바뀌면 갱신한다.
2. **셸**: **이미 60Hz로 도는 폴링**(`mac/Sources/main.swift:200` `pollKeys`) 안에서
   커서 위치를 읽는다 — `NSEvent.mouseLocation` / 윈도우 `GetCursorPos`.
   둘 다 **손쉬운 사용 권한이 필요 없고 이벤트를 삼키지도 않는다**(수식키 폴링과 같은 성질).
   `커서가 히트박스 안 && 수식키 누름` → `ignoresMouseEvents = false`,
   아니면 `true`. **셸이 하는 일은 이 토글 하나뿐이다.**
3. **웹뷰**: 문이 열리면 평범한 포인터 이벤트가 들어온다.
   드래그는 `app.js`의 `pointerdown / pointermove / pointerup`이다.
4. **드래그 중에는 히트박스를 넓힌다.** `pointerdown` 시점에 게임이 필드 전체 크기의
   히트박스를 다시 밀어 준다. 안 그러면 커서가 투수보다 빨리 움직이는 순간 문이 닫혀
   드래그가 끊긴다. `pointerup`에서 원래 크기로 되돌린다.
5. **잡을 수 있다는 표시.** 수식키를 누른 채 커서가 투수 위에 오면 투수 발밑에 표시가
   뜬다. 없으면 드래그가 가능한지 알 길이 없다.

### 저장

고른 위치는 셸이 저장한다 — 맥 `UserDefaults`, 윈도우 `state.json`.
유니폼·모니터·조작키가 이미 쓰는 길 그대로다. 브리지에 `sneaky.pitcherX`(초기값)와
`sneaky.onPitcherX`(바뀔 때)를 더하고, 게임이 놓을 때 `sneaky.savePitcherX(v)`를 부른다.

브라우저로 열었을 땐 클릭 통과 개념이 없으니 그냥 드래그된다. 저장은 `localStorage`.

## 6. 기록은 하나로 둔다

지금 그대로 `최고 비거리(m)` 하나다. 거리별로 가르지 않는다.

**대신 이 사실을 적어 둔다: 난이도가 기록에 섞인다.** 투수를 멀리 밀면 반응 시간이
늘어 좋은 타이밍을 맞추기 쉬워지고, 거기서 세운 기록이 같은 자리에 올라간다.
이동 범위를 ±15%로 좁게 잡는 이유가 이것이다. **범위를 넓히려면 기록을 갈라야 한다.**

## 남은 판단

- **`START_X`·`RUN_SPEED`·`REACH` 값은 만들어 보고 맞춘다.** 표의 네 줄이 실제로 그렇게
  갈리는지가 기준이다. 야수가 너무 잘 잡으면 안타가 사라지고, 못 잡으면 세운 의미가 없다.
- **투수 이동 범위 ±15%도 만들어 보고 맞춘다.** 눈에 띄게 달라지되 기록 왜곡이
  작아야 하는데, 이 둘이 서로 반대 방향이다.
- **클릭 통과 예외가 실제로 거슬리는지는 써 봐야 안다.** 투수는 화면 왼쪽 아래 구석에
  있어 밑에 뭐가 있을 일이 드물지만, 거슬리면 히트박스를 더 줄이거나 A안(커서를 대면
  따라온다)으로 되돌린다. 예외가 한 군데뿐이라 되돌리기 쉽다.
